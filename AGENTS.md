# AGENTS.md

**Agent guide for working in the asyncfiles codebase**

This document provides essential context for AI agents working in this repository. It covers commands, code organization, conventions, and gotchas.

---

## Project Overview

**asyncfiles** is a high-performance async file I/O library for Python, built on libuv (and io_uring on Linux) using Cython. It provides true asynchronous file operations without blocking the event loop.

- **Language**: Python 3.10+ with Cython 3.0 extensions
- **Architecture**: Cython-compiled C extensions with two interchangeable backends: `libuv` (default everywhere) and `io_uring` (Linux kernel >= 5.6, selected by `backend="auto"` when a runtime probe succeeds)
- **Current Status**: Alpha/experimental - API may change. The version is managed by semantic-release (see `pyproject.toml`), not by hand
- **Platform Support**: Linux, macOS, BSD and Windows (libuv backend only on Windows; libuv is built with CMake there)

### Module Architecture

**Layered design** from low-level to high-level:

1. **libuv bindings** (`uv.pxd`) - C API declarations
2. **Utilities** (`utils.pyx`, `memory_utils.pyx`, `callbacks.pyx`) - Helper functions
3. **Buffer management** (`buffer_manager.pyx`) - Dynamic buffer allocation
4. **Event loop integration** (`event_loop.pyx`) - EventLoopPump bridges libuv and asyncio
5. **I/O operations** (`io_operations.pyx`) - IOOperation wraps libuv file operations
6. **File I/O** (`file_io.pyx`) - FileReader/FileWriter orchestrate reads/writes
7. **File abstractions** (`base_file.pyx`, `binary_file.pyx`, `text_file.pyx`) - User-facing classes
8. **Public API** (`__init__.py`) - `open()` returns the file object, which is itself the async context manager (`BaseFile.__aenter__`/`__aexit__`); it is deliberately not an `@asynccontextmanager` generator (measured overhead on small files)

The io_uring backend (`io_uring_*.pyx`) replaces layers 4-6 on Linux; `BaseFile` dispatches on `self.backend`. Both backends must keep identical behavior; the test suite enforces this.

**Key classes:**

- `FileMode` - Parsed file mode (readable, writable, binary, flags, etc.)
- `EventLoopPump` - Runs libuv loop to pump async events
- `IOOperation` - Wraps a single file descriptor with libuv operations
- `BufferManager` - Allocates/frees uv_buf_t buffers efficiently
- `FileReader` / `FileWriter` - Orchestrate chunked reads/writes
- `BaseFile` - Base class with common file operations (seek, tell, truncate)
- `TextFile` / `BinaryFile` - Mode-specific implementations (UTF-8 vs bytes)

## Cython Patterns and Conventions

### File Headers

Every `.pyx` file starts with:
```cython
# distutils: language = c
# cython: language_level=3
# cython: boundscheck=False
# cython: wraparound=False
```

### Import Conventions

```cython
from . cimport uv                  # libuv bindings
from . cimport cpython as py       # CPython API
from .utils cimport FileMode       # Internal Cython imports
from cpython.ref cimport Py_INCREF, Py_DECREF
from libc.stdlib cimport malloc, free
from libc.stdint cimport int64_t
```

### Memory Management

**Critical**: Manual memory management is required for C allocations.

```cython
# Always pair malloc with free
cdef uv.uv_buf_t* bufs = <uv.uv_buf_t*>malloc(count * sizeof(uv.uv_buf_t))
if bufs == NULL:
    return NULL
# ... use bufs ...
free(bufs)

# Use nogil for performance-critical sections
cdef inline uv.uv_buf_t* _make_uv_bufs(...) noexcept nogil:
    # No Python objects allowed here
    pass

# Manage Python refcounts when storing in C structures
Py_INCREF(future)  # Keep Python object alive
# ... later ...
Py_DECREF(future)  # Release reference
```

### Error Handling

```cython
# Check libuv return codes
cdef int err = uv.uv_fs_open(...)
if err < 0:
    raise OSError(err, uv.uv_strerror(err))

# Check C allocations
if ptr == NULL:
    raise MemoryError("Allocation failed")
```

### Async Integration

```cython
# Create an asyncio Future from C code (see asyncfiles/utils.pyx)
cdef object new_future(object loop):
    return loop.create_future()
```

**Reference ownership**: `new_future` returns a plain future and takes *no* extra reference. The caller that stores the future in a C context does its own `Py_INCREF`, and the libuv callback does the matching `Py_DECREF` exactly once. An extra `Py_INCREF` inside `new_future` once leaked every Future (148k objects in the benchmark, `test_open_does_not_leak_futures` guards it).

## Coding Conventions

### Python Code

- **PEP 8 compliant** (enforced by black/isort)
- **Line length**: 88 characters (black default)
- **Type hints**: Required for public APIs (`__init__.pyi` provides stubs)
- **Docstrings**: Required for public functions/classes
- **Import order**: stdlib → third-party → local (enforced by isort with black profile)

### Cython Code

- **Use `cdef` for performance-critical functions**
- **Use `cpdef` for functions called from both Python and Cython**
- **Use `@cython.cdivision(True)` for faster integer division**
- **Avoid Python object overhead** in tight loops (use C types)
- **Release GIL** with `nogil` in pure C sections
- **Mark exception-less functions** with `noexcept` (Cython 3.0)

### Naming Conventions

- **Python**: `snake_case` for functions, `PascalCase` for classes
- **Cython internal**: Prefix with `_` (e.g., `_make_uv_bufs`, `_read_internal`)
- **C variables**: `snake_case` with type prefixes where helpful (e.g., `data_ptr`, `chunk_len`)

## File Mode System

The library uses a custom `FileMode` class to parse Python file mode strings into POSIX flags.

**Supported modes:**
- Base: `r` (read), `w` (write+truncate), `a` (append), `x` (exclusive create)
- Modifiers: `+` (read+write), `b` (binary), `t` (text, default)
- Examples: `r`, `w`, `rb`, `w+`, `a+b`, etc.

**Mode parsing** (`utils.pyx::mode_to_posix`):
```python
from asyncfiles.utils import mode_to_posix
mode = mode_to_posix(b"w+b")  # Returns FileMode instance
# mode.readable == True
# mode.writable == True
# mode.binary == True
# mode.flags == O_CREAT | O_TRUNC | O_RDWR
```

**Mode selection** (`__init__.py::open`):
```python
FileClass = BinaryFile if file_mode.binary else TextFile
```

## Common Gotchas

### 1. **Windows uses a separate build path**

On Windows `setup.py` builds libuv with CMake (`build/libuv-<arch>/Release/libuv.lib`) and links the system libraries (`ws2_32`, `iphlpapi`, ...). libuv error codes are not errno there (e.g. `UV_ENOENT == -4058`), so `callbacks.pyx::_uv_oserror` translates them through `uv_err_name`. Never build `OSError(-err, ...)` directly from a libuv status. `io_uring` does not exist on Windows.

### 2. **Generated C files are NOT tracked in git**

`asyncfiles/*.c` is in `.gitignore`. After modifying `.pyx` files run `make compile` to regenerate them locally; never commit them. Released sdists/wheels are built by CI.

### 3. **libuv is a git submodule**

The `vendor/libuv/` directory is a submodule. After cloning:
```bash
git submodule init
git submodule update
```

CI/CD (`.github/workflows/release.yml`, `tests.yml`) does this automatically (`submodules: true`).

### 4. **File offset tracking is manual**

`BaseFile` maintains `self.offset` manually - not via OS file descriptor position. This is intentional for async flexibility but requires careful tracking in read/write operations.

```cython
# In text_file.pyx
async def read(self, int length=-1):
    data = await self._read_internal(total_to_read)
    if self.offset >= 0:
        self.offset += len(data)  # Manual tracking!
    return data.decode("utf-8")
```

### 5. **EventLoopPump must be started and stopped**

The `EventLoopPump` runs libuv's event loop to process async operations. It's created in `BaseFile.__init__` and managed in `__aenter__`/`__aexit__`.

**Critical**: Always use context managers (`async with`) to ensure proper cleanup.

### 6. **Buffer size is configurable but has heuristics**

Default buffer size is 64KB. `BufferManager` dynamically adjusts:
- Small reads (< buffer_size): Single buffer
- Large reads (> 10MB): 2MB chunks, max 64 buffers
- Medium reads: Use buffer_size chunks, max 64 buffers

See `buffer_manager.pyx::create_read_buffers` for logic.

Writes are sliced into `buffer_size` pieces by `create_write_buffers`. `TextFile.write` passes the `str` straight to the writer, which uses `PyUnicode_AsUTF8AndSize` and keeps the `str` alive (`ctx._refs`) while the write is in flight. Do not re-introduce an intermediate `bytes` copy.

### 7. **Semantic versioning is automated**

Commits use [Conventional Commits](https://www.conventionalcommits.org/):
- `feat:` → minor version bump
- `fix:` / `perf:` / `refactor:` → patch version bump
- `BREAKING CHANGE:` footer or `!` after the type → major version bump
- `docs` / `test` / `build` / `ci` / `chore` → no release

`.github/workflows/release.yml` runs `python-semantic-release` on pushes to `main`. Never edit versions or `CHANGELOG.md` by hand.

### 8. **Type checking ignores asyncfiles module**

`pyproject.toml` has:
```toml
[[tool.mypy.overrides]]
module = "asyncfiles.*"
ignore_errors = true
```

**Reason**: Cython-generated code confuses mypy. Type hints are provided via `__init__.pyi` stub files instead.

### 9. **No runtime dependencies**

The package has **zero runtime dependencies** (`install_requires=[]`). It's fully self-contained once compiled.

### 10. **Branch strategy**

`main` is the only long-lived branch and every push to it runs the release pipeline. Develop in short-lived feature branches and PR to `main`; PR titles must follow Conventional Commits (`pr-title.yml`). semantic-release handles versioning/publishing.

1. **Identify layer**: Determine if the feature belongs in:
   - Low-level (buffer management, I/O operations)

3. **Add tests**:
   - Create test functions in `tests/test_files.py`

5. **Benchmark if performance-critical**:
   - Add benchmark in `benchmark/` if adding I/O-related features

## Debugging Tips

### Enable Cython Line Tracing

```bash
make debug
pytest tests/ -v
```

This builds with `linetrace=True` and generates `.html` annotation files showing C/Python boundary.

### Enable Asyncio Debug Mode

```bash
PYTHONASYNCIODEBUG=1 pytest tests/ -v
```

Shows warnings for:
- Futures that were never awaited
- Tasks destroyed but pending
- Event loop running in wrong thread

### Check libuv Errors

libuv errors are negative integers. Convert to string:
```python
import asyncfiles.uv as uv
print(uv.uv_strerror(err))
```

### Inspect Generated C Code

After `make compile`, check `asyncfiles/*.c` files to see what Cython generated. Useful for understanding performance issues.

### Use gdb with Cython

```bash

gdb --args python -m pytest tests/test_files.py::test_read
```

Cython line tracing helps gdb show Python line numbers.

## Performance Considerations

### Key Optimization Strategies

1. **Zero-copy buffers**: reads land directly in the result `bytes`; text writes go straight from the `str`'s UTF-8 buffer
2. **Chunked I/O**: large reads use multiple buffers (libuv) or parallel 2MB SQEs (io_uring, `PARALLEL_THRESHOLD` = 4MB)
3. **Manual offset tracking**: Avoids lseek() syscalls
4. **Cython `nogil` sections**: Release GIL during C operations
5. **Static libuv linking**: Avoids dynamic library overhead
6. **`fstat(fd)`** on the open descriptor instead of `stat(path)` (no path re-resolution race)

### Measured findings (Docker, 2 CPUs / 2GB, interleaved A/B, median)

Only keep an optimization if an interleaved A/B shows it beats the noise:
- Kept: zero-copy text write (5MB text write -68% libuv / -76% io_uring), no `asynccontextmanager` in `open()` (4k ops -16..-33%), Future leak fix (RSS -26%).
- Rejected (no measurable gain): single `pwrite` buffer for writes, disabling io_uring write chunking.
- Rejected (regression): raising io_uring `PARALLEL_THRESHOLD` so reads are no longer chunked (+72% on 16MB reads); shrinking the libuv threadpool from 8 to 4 (+17% on 16MB reads).
- Known quirk: `libuv.a` is linked statically into each extension module, so there are several libuv copies and thus several thread pools (8 `libuv-worker` threads observed).
- Compare sequential runs only with care: host load makes them drift by 10-30%. Run A and B interleaved, several rounds.

### Benchmarking

Always benchmark changes against `aiofiles`, `aiofile` and `anyio` (the harness is `benchmark/benchmark_docker.py`, built by `Dockerfile.benchmark`):
```bash

```

Results (`benchmark/results/benchmark_read.md`, `benchmark_write.md`) are

## CI/CD

### Release Workflow

File: `.github/workflows/release.yml` (triggers: push to `main`, `workflow_dispatch`)

**Jobs**:
1. `test` — reuses `tests.yml` (Python 3.10–3.15 on ubuntu/macos)
2. `version` — `python-semantic-release` bumps `pyproject.toml` / `asyncfiles/__init__.py`, updates `CHANGELOG.md`, commits `chore(release): X.Y.Z [skip ci]`, creates the `vX.Y.Z` tag and the GitHub release (only if the commits warrant a release)
3. `build-sdist`, `build-wheels` — built from the new tag (cibuildwheel, Python 3.10–3.15)
4. `publish` — attaches dists to the GitHub release and publishes to PyPI via trusted publishing (environment `pypi`). The PyPI trusted publisher must list **workflow `release.yml`** (a mismatched workflow name fails with `invalid-publisher`)
5. `benchmark` — runs `scripts/run_docker_benchmark.sh` on the tag, attaches `benchmark_read.md`/`benchmark_write.md` to the release and commits them to `main`

Everything runs in one workflow because tags pushed with `GITHUB_TOKEN` do not trigger other workflows. A `release` concurrency group (`cancel-in-progress: false`) serializes runs, so a newer push waits behind (and may supersede) a pending one.

**Semantic release config** in `pyproject.toml` (`[tool.semantic_release]`):
- Version lives in `pyproject.toml:project.version` and `asyncfiles/__init__.py:__version__` (keep them equal)
- Validate locally with `semantic-release --noop version --print`
